P0 闪屏图标在主线程同步解码 — 系统 trace 那 828ms 的真凶

app/src/main/java/com/tracktosearch/MainActivity.kt:355-360（启动闪屏/引导动画里）

val context = LocalContext.current
val launcherBitmap = remember {
    android.graphics.BitmapFactory.decodeResource(
        context.resources, R.drawable.ic_search_cloud
    )?.asImageBitmap()   // ← 合成阶段在主线程同步解码
}

问题：remember { BitmapFactory.decodeResource(...) } 在首次组合（闪屏）时于主线程同步解码 ic_search_cloud，且 decodeResource 不解采样、按固有分辨率解码 → 直接造成启动期 828ms 卡顿（与系统 trace 中 resume 后约 367ms 出现的 1513ms 冻结帧吻合）。remember 只保证不重复解码，但第一次依然是同步的。

修复（不改功能/视觉）：

  • 最简洁：把 Image(bitmap = launcherBitmap, ...) 换成 Image(painter = painterResource(R.drawable.ic_search_cloud), ...)。Compose 的 painterResource 走异步加载，不会在主线程 BitmapFactory.decodeResource。
  • 若确实需要 ImageBitmap（用于后续缩放/裁剪动画）：在 Application/启动协程里用 Dispatchers.IO 预解码一次并缓存结果，组合时直接取已解码的位图；或改用 Coil 的 AsyncImage/ImageRequest 加载该 drawable。
  • 顺带：确认 ic_search_cloud 分辨率是否过大（闪屏仅显示 ~211dp），必要时提供匹配密度的资源或 inSampleSize 降采样。

P0 Discover 屏 lazy 列表的“测量风暴”是主线程头号耗时

主线程调用频次 Top（结构可靠，时长因导入放大见⑤）：

方法调用次数含义
Float.floatToRawIntBits / intBitsToFloat14.0万 / 13.0万布局位置/偏移的 float↔bits 换算，测量越多越高
Intrinsics.areEqual / Object.equals12.0万 / 9.5万状态比较（重组/相等性判断）
LayoutNode.getParent / getDepth6.3万布局树遍历

MutableVector.getSize / ArrayList.get5.4/3.8万列表/集合遍历（measure 子节点）

热点调用链（来自方法树）：LookaheadPassDelegate.performMeasure → ColumnMeasurePolicy.measure → LazyListMeasure(measureLazyList) → LazyLayoutMeasuredItemProvider.getPlaceables → subcompose → ComposableLambda(DiscoverSections/TraktTrendingMovieSection/TmdbMovieSection → MovieCard)。即 Discover 屏的多个横向/纵向 LazyList 区块（每个区块一张张 MovieCard）在反复测量/重组。

线索：调用栈里反复出现 LookaheadPassDelegate。若 Discover 屏用了 AnimatedVisibility / AnimatedContent / LookaheadScope / Modifier.sharedBounds（共享元素/转场），会触发 lookahead 测量使整棵子树测量翻倍。建议核查 DiscoverScreen/DiscoverSections 是否引入这类动画，并尽量缩小其作用范围。

修复方向（均不改功能）：

  • 给 LazyList 各 item（MovieCard）加稳定 key，并把卡片的 DTO 标 @Immutable/@Stable，减少因不稳定对象导致的整项重组。
  • 收敛状态：卡片内 remember 提取稳定值，避免在 item 组合闭包里创建新 lambda/新对象（每次测量都新建 → 上面 27 万次 float 换算与 9.5 万次 equals 的来源之一）。
  • 若区块内容高度固定，给容器显式约束高度，避免 LazyList 在测量期反复估算。
  • 非首屏区块做懒加载/分页，减少同屏被测量的 item 数。

好消息 影片图片管线本身没问题，别动它

Method trace 显示：主线程上所有 Bitmap 相关调用都是亚毫秒级（BitmapPainter.onDraw 0.25ms、Bitmap.createBitmap 1.2ms），没有 BitmapFactory.decodeStream 出现在主线程。图像像素解码发生在后台线程（OkHttp image.tmdb.org 与协程 IO 调度器），由 Coil（coil.RealImageLoader、DefaultRequestOptions.getBitmapConfig）负责。

结论：上一版报告里把“图片解码”列为 P0 是方向对、但具体到影片图是误伤——影片图走 Coil 已经在后台解码。真正的主线程同步解码只有上面 P0 的闪屏图标一处。所以优化重点是“闪屏图标”+“Discover 屏测量”，而不是替换图片库。

⑤ 数据可信度说明（重要）

本 Method trace 经 Perfetto 导入后，调用结构、方法名、调用频次 100% 可靠；但 measure/recompose 子树的绝对时长被放大（主线程 699 万次切片中 4.3 万次 >1s、476 次 >1000s，疑似时钟/出序导致该子树 entry/exit 配对失真）。因此本报告的方法级结论基于“调用路径 + 频次”，而整体严重度仍以系统 trace 的实测帧耗时（平均 113ms、最差 1931ms）为准。

想要精确 ms：用 Android Studio 重新录一段 5–10 秒的 Method Trace，只复现“进入 Discover 屏 / 点开详情”这一步，避免长录制触发时长失真；或直接用 release 包 + System Trace 复测帧耗时验证。闪屏图标那 828ms 已可凭源码定位直接修。

⑥ 修订后的优先级（综合两份 trace）

  1. P0 改闪屏图标加载：MainActivity.kt:357 去掉主线程 BitmapFactory.decodeResource，改用 painterResource 或后台预解码。直接消除启动 828ms 卡顿。
  2. P0 收敛 Discover 屏测量/重组：LazyList item 加 key + DTO @Immutable + 提取稳定状态 + 缩小动画 lookahead 范围。削减 992/943ms 级重组与测量。
  3. P1 降低测量期分配：减少组合闭包里的临时对象/装箱（对应 27 万次 float 换算、9.5 万次 equals），缓解 GC 2.15s。
  4. P2 启动初始化移出主线程：WorkManager 等（系统 trace 见 150ms 阻塞）继续按前报告处理。

注：影片图片的 Coil 异步解码、TtlCache/持久化缓存（见 AGENTS.md）保持现状即可，无需为性能改动。
