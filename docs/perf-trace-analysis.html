③ 可优化点（均不改变功能性，仅优化性能）

优先级问题 / 证据建议修复
P0 主线程同步解码 Bitmap（decodeBitmap）
2 次调用，共 835ms，单次最长 828ms，发生在首屏加载帧内		 UI 线程直接做 BitmapFactory.decode*，阻塞渲染。应使用 Coil/Glide 异步解码并在 IO 线程完成；按显示尺寸申请缩略图（inJustDecodeBounds + sampleSize / 指定 TMDB 缩略图尺寸）。
P0 GC 压力极高（内存抖动）
71 次 GC，累计 2151ms，单次最长暂停 932ms（HeapTaskDaemon 9 次共 2082ms）		 热路径上大量临时对象分配（重组 lambda、JSON 解析、Bitmap）。热点加 @Stable/@Immutable、复用对象、避免重组内分配；图片按尺寸解码可显著降低 Bitmap 内存与 GC。
P0 过度重组（Compose:recompose）
多次大重组：943ms / 855ms / 420ms / 204ms		 LazyColumn item 未加 key、数据类非稳定、状态提升不当导致整树重算。给列表项加 key、将 DTO 标为 @Immutable、用 derivedStateOf、上移状态，减少不必要重组。
P1 首帧绘制过晚 / 冷启动慢
bindApplication 745ms；进程启动→Resume 约 1474ms；首屏完整绘制约 3.3s		 WorkManager 在主线程初始化阻塞 150ms；LZ4 解压/base.apk 加载。把 WorkManager 从 androidx.startup 移除或在后台线程初始化；确认启动只做必要工作。
P1 主线程等待 GPU（postAndWait）
最长 548ms，多次 400-500ms		 RenderThread 绘制大图/过度绘制导致主线程同步等待。缩小图片纹理尺寸、降低重叠背景过度绘制、合理使用 clip，减轻 GPU 负担。
P1 详情页网络串行 / 未充分利用缓存
详情页触发 trakt+tmdb+omdb 多请求，重组由数据到达驱动，帧耗时 100-470ms		 请求应并发发起；按 AGENTS.md 既有 TtlCache/持久化缓存（movieDetailCache 等）在返回/前进时命中，避免每次重新拉取与重解码。
P2 锁竞争阻塞主线程
WorkManager.getInstance 监视器竞争 150ms；多处 thread-list / ClassLinker 锁 10-67ms		 避免在主线程调用会等待后台锁的初始化；启动期热点加锁操作前移或异步化。
P2 应用进程疑似多次重建
trace 内含 3 个进程实例（pid 17035/17211/17450）		 若非用户主动重启，需排查被 LMK/OOM 杀掉（大图 Bitmap 占用过高）。确认后降低内存峰值可避免重复冷启动。

④ 根因小结与建议顺序

占主导的是图片处理链路：主线程同步解码（828ms）+ 全尺寸绘制导致 GPU 等待（postAndWait 500ms+）+ 大 Bitmap 带来内存抖动（GC 累计 2.15s）。它被过度重组放大（943/855ms 重组），并在冷启动因 WorkManager 主线程初始化额外阻塞 150ms。

  • 第一步（收益最大）：图片改为异步加载并严格按显示尺寸解码/缓存 → 同时削减 decodeBitmap、GC、postAndWait 三项。
  • 第二步：治理重组（key / @Immutable / derivedStateOf / 状态上移）→ 削减 943/855ms 重组与伴随分配。
  • 第三步：启动期把 WorkManager 等初始化移出主线程；详情页请求并发 + 复用既有 TtlCache/持久化缓存。
  • 第四步：排查进程疑似多次重建（大图内存峰值 → LMK 杀进程），降低内存峰值。

说明：system trace 为 atrace 级别，未含方法级采样，因此“重组/解码”等为系统切片级推断；如需精确到具体 Compose 函数，建议补一次 Method/Java 采样 trace 复测。
