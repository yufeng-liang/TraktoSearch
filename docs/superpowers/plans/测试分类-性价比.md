## 测试金字塔（从下到上）

### 第1层：单元测试（Unit Test）

**测什么：** 单个类/函数的内部逻辑，隔离所有外部依赖

**特点：**
- 在 JVM 运行（不需要手机/模拟器）
- 毫秒级速度，可跑几百个
- 用 mock 替换依赖（网络、数据库、Context）

**你已有的 247 个测试都是这层：**
- `AesCryptoTest` — 测加密函数输入输出
- `TtlCacheTest` — 测缓存过期/容量逻辑
- `UpdateRepositoryTest` — 测版本比较、降级链路（mock 掉 GitHub/Gitee API）
- `DoubanSyncManagerTest` — 测 `restoreRollback` 分类逻辑（mock 掉 DAO 和 TraktRepository）

**能发现的 bug：** 算法错误、边界条件、空值处理、状态机错误
**不能发现：** UI 渲染问题、组件交互、真实网络异常、数据库 schema 问题

---

### 第2层：ViewModel 测试（仍是单元测试，但有状态）

**测什么：** ViewModel 的状态管理——用户操作如何改变 StateFlow，业务逻辑如何执行

**特点：** 仍在 JVM 运行，用 `turbine` 测试 Flow，用 `MainDispatcherRule` 替换协程调度器

**举个你的 App 的例子：**

```kotlin
// 用户在搜索页输入"盗梦空间"
// 期望：uiState 变为 Loading → Success，results 包含匹配结果
@Test
fun search_输入关键词_状态变为Loading然后Success() = runTest {
    // mock TraktRepository.search 返回固定结果
    coEvery { repo.search("盗梦空间") } returns listOf(fakeMovie)
    
    viewModel.onSearchQueryChange("盗梦空间")
    
    // 用 turbine 验证 StateFlow 状态变化序列
    viewModel.uiState.test {
        assertThat(awaitItem()).isInstanceOf(Loading::class.java)
        val success = awaitItem()
        assertThat(success).isInstanceOf(Success::class.java)
        assertThat((success as Success).results).hasSize(1)
    }
}
```

**能发现的 bug：**
- 状态流转错误（Loading 卡住、状态不重置）
- 协程取消问题（用户快速切页面时请求泄漏）
- 业务逻辑错误（标记想看后 UI 状态没更新）
- 错误处理（网络失败时 UI 显示什么）

**性价比：极高** — 复用你现有基础设施，无需设备，覆盖大部分业务逻辑

### 第3层：Compose UI 测试（Instrumented Test）

**测什么：** Compose 组件的渲染和交互——按钮点击、列表滚动、导航跳转、状态显示

**特点：**
- 在手机/模拟器运行（`androidTest` 目录）
- 秒级速度（比单元测试慢，比 E2E 快）
- 用 `ComposeTestRule` 查找组件、模拟点击、验证显示
- 需要 mock 或真实依赖

**举个你的 App 的例子：**

```kotlin
// 用户点击搜索结果中的电影卡片，应该跳转到详情页
@Test
fun searchResults_点击电影卡片_导航到详情页() {
    val navController = TestNavController()
    
    composeTestRule.setContent {
        SearchScreen(
            uiState = SearchUiState.Success(listOf(fakeMovie)),
            onMovieClick = { movieId -> navController.navigate("detail/$movieId") }
        )
    }
    
    // 验证卡片显示
    composeTestRule.onNodeWithText("盗梦空间").assertIsDisplayed()
    
    // 模拟点击
    composeTestRule.onNodeWithText("盗梦空间").performClick()
    
    // 验证导航发生
    assertThat(navController.currentDestination?.route).isEqualTo("detail/{movieId}")
}
```

**能发现的 bug：**
- 组件渲染错误（数据有但不显示、显示错位）
- 交互逻辑错误（点击没反应、点击跳错页）
- 可访问性问题（无障碍标签缺失）
- 列表滚动/分页问题
- Compose 重组性能问题（用 `Benchmark` 进一步测）

**性价比：高** — 能发现 UI 层特有 bug，但需要设备/模拟器

### 第4层：端到端集成测试（E2E / Integration Test）

**测什么：** 完整用户流程，从 UI 点击到网络请求到数据库写入，全链路验证

**特点：**
- 在手机/模拟器运行
- 用 `MockWebServer` 模拟 API 响应（替代真实网络）
- 用测试数据库（内存 Room）
- 用 Hilt 测试规则注入真实依赖（非 mock）
- 最慢，但最接近真实用户体验

**举个你的 App 的例子：**

```kotlin
// 完整流程：搜索电影 → 查看详情 → 标记想看 → 验证想看列表出现
@Test
fun searchToDetailToWatchlist_完整流程() = runTest {
    // MockWebServer 返回预设的搜索结果和详情
    mockWebServer.enqueue("/search", searchResponseJson)
    mockWebServer.enqueue("/movies/detail", detailResponseJson)
    
    // 启动 App（用 Hilt 注入真实依赖，但网络指向 MockWebServer）
    launchActivity<MainActivity>()
    
    // 在搜索框输入
    onNodeWithText("搜索").performTextInput("盗梦空间")
    // 等待结果显示
    waitForNodeWithText("盗梦空间").assertIsDisplayed()
    // 点击
    onNodeWithText("盗梦空间").performClick()
    // 详情页显示
    waitForNodeWithText("克里斯托弗·诺兰").assertIsDisplayed()
    // 点击"想看"按钮
    onNodeWithText("想看").performClick()
    // 导航到想看列表
    onNodeWithContentDescription("想看").performClick()
    // 验证刚标记的电影在列表中
    onNodeWithText("盗梦空间").assertIsDisplayed()
}
```

**能发现的 bug：**
- 集成层 bug（ViewModel + Repository + DAO 组合时出错，单测都过但组合失败）
- 数据流问题（Repository 返回格式和 ViewModel 消费格式不匹配）
- 导航图错误（路由参数传递错误）
- 真实协程调度问题

**性价比：中** — 覆盖最广但维护成本高，每个测试需要大量 setup

## 我之前说的"集成测试范畴"是什么意思

`DoubanSyncManager.startSync()` 这个方法内部调用了：
- `doubanRepository.fetchMarkList()` — 真实爬豆瓣网站
- `traktRepository.batchAddToWatchlist()` — 真实调 Trakt API
- `cloudPersonalSyncManager.uploadAll()` — 真实调 Gitee API
- 多个 DAO 读写
- 协程调度、WakeLock、并发控制

**单元测试要 mock 掉所有这些**，否则跑不起来。但 mock 掉之后，测的是"假设所有依赖按预期工作，协调逻辑是否正确"——这价值有限，因为 bug 往往出在**组合**上（比如豆瓣返回的字段格式和 Trakt 期望的不匹配）。

要测这种组合 bug，需要 E2E 集成测试（第4层），用 MockWebServer 模拟豆瓣/Trakt 的 HTTP 响应，让真实代码完整跑一遍。但这投入大，所以我当时说"集成测试范畴"——意思是"如果你想测这个，应该用集成测试而非单元测试"。

**不建议现在做：**
- E2E 全链路测试（投入产出比低，等前两层稳定后按需补充）
- 性能测试（你的App性能问题不突出）
