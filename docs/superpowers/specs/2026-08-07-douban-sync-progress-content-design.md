# 豆瓣同步阶段进度信息保真设计

## 背景与目标

同步对话框目前始终复用 `recentItems`。该字段只在豆瓣想看/看过列表抓取时更新，进入详情解析、Trakt ID 匹配和写入阶段后仍显示旧列表内容，用户无法判断当前真正处理的条目。

本次目标：

1. 让每个同步阶段只展示属于该阶段的条目信息。
2. 让“正在处理”和“待处理”来自同步批次的真实条目队列，而不是由 UI 根据数量猜测。
3. 让对话框、前台通知和 Watchlist 横幅共用同一套阶段语义。
4. 将状态一致性检查、个人数据上传、失败项上传和详情池上传纳入同步生命周期，上传未结束前不发布“同步完成”。
5. 保持取消、续传、重试、豆瓣独立模式和双登录模式的现有业务语义。

## 不在范围内

- 不改变豆瓣列表抓取、详情解析、Trakt 查询或本地写入的业务结果。
- 不把并发任务伪装成单个确定的“当前网络请求”；界面只展示同步层能确认的活动条目。
- 不在进度对象中持久化完整队列；断点续传仍由 pending items 表恢复。
- 不新增独立的同步历史页面。

## 方案选择

采用显式批次队列方案。同步层维护当前批次的活动条目和待处理条目，并在真实条目开始处理、处理完成、批次切换时更新进度对象。UI 只负责按阶段渲染，不再从 `recentItems` 或 `current/total` 推断条目内容。

相比只改文案，这种方式可以处理同名条目、并发回调乱序和断点跳过；相比为每个阶段建立独立持久化快照，改动集中在内存进度模型和现有 StateFlow，不增加恢复协议。

## 进度模型

新增轻量条目类型：

```kotlin
data class DoubanSyncQueueItem(
    val doubanId: String,
    val title: String
)
```

`DoubanSyncProgress` 新增：

- `processingItems`：当前批次已开始、尚未完成的条目，保留稳定顺序并限制 UI 展示数量。
- `pendingItems`：当前批次尚未开始的条目，保留稳定顺序并限制 UI 展示数量。
- `pendingItemCount`：尚未开始条目的完整数量，用于“还有 N 项待处理”汇总。

旧的 `currentTitle` 保留作为通知和兼容调用方的单条摘要，取当前活动条目的首项；`recentItems` 只保留列表抓取阶段和完成态的历史摘要用途。

批次队列按 `doubanId` 更新：

- 详情抓取或 Trakt 查询真正开始前，将条目移入 `processingItems`。
- 详情失败、无 IMDb、Trakt 查询完成或本地写入完成后，从活动队列移除。
- 跳过项不进入待处理队列，但仍计入阶段的 `current/total`，避免数量口径变化。
- 新批次开始时清空上一批队列；列表抓取阶段切换 WISH/COLLECT 时清空旧的“最近获取”摘要。

## 阶段展示规则

| 主阶段 | 子阶段 | 条目区域 | 进度语义 |
|---|---|---|---|
| 准备 | 连接、拉取云端 | 不显示条目列表 | 显示当前准备操作，不复用旧条目 |
| 获取列表 | 想看、看过列表 | 显示“最近获取” | 仅展示当前列表抓取得到的最近条目 |
| 解析数据 | 详情页、Trakt 查询、失败重试 | 显示“正在处理”和“待处理” | 队列来自当前批次，最多展示 3 个活动项和 5 个待处理项，其余显示数量 |
| 更新列表 | 状态变化、写入 Trakt、本地写入 | 清空条目队列 | 显示真实的批量写入/状态更新操作，不把上一阶段标题当成当前条目 |
| 云端同步 | 状态一致性、个人数据、失败项、详情池 | 清空条目队列 | 显示当前上传/检查操作，完成前保持运行态 |
| 终态 | 完成、取消、登录要求、失败 | 不显示运行中队列 | 显示最终统计或错误详情 |

### 并发语义

详情抓取并发度为 3、Trakt 查询并发度为 5。`processingItems` 表示同步层仍在处理的条目集合，不承诺只有一个条目。UI 使用“正在处理”复数语义，避免把并发流水线误报为单线程顺序处理。

### 数量语义

`current/total` 继续表示当前批次已完成或跳过的条目数与批次总数；云端上传和状态检查阶段不沿用条目批次数量，使用不定进度或阶段专属状态，避免把 461 条解析进度误套到上传操作上。

## 云端同步生命周期

现有流程在本地同步结果生成后立即发布终态，随后才执行云端同步。改为：

1. 本地列表、详情、匹配和写入全部结束。
2. 发布 `UPLOADING` 运行态，清空条目队列。
3. 执行状态一致性检查、个人数据上传、失败项上传、详情池上传和媒体类型补全。
4. 所有辅助上传操作结束后发布完成；取消仍由取消路径上传部分进度并保持取消语义。

辅助上传失败继续遵循现有“不阻塞主同步”的策略，但运行期间必须显示对应阶段；一致性检查抛出的主流程异常进入失败终态。

## UI 与通知

`DoubanSyncDialog` 根据 `stage` 渲染阶段专属区域：

- 列表阶段使用现有卡片摘要，但标题改为阶段明确的“最近获取”。
- 解析阶段分别渲染活动条目和待处理条目，最多展示约定数量，并展示剩余总数。
- 更新/上传阶段隐藏上一阶段的条目卡片，仅保留阶段、数量和 ETA/等待信息。

`DoubanSyncService` 的通知正文优先使用当前阶段和活动条目；上传阶段不回退到 `recentItems`，避免通知继续显示旧列表标题。横幅继续读取稳定阶段标签。

## 错误、取消和恢复

- 列表抓取失败：保留登录过期终态，不显示旧批次队列。
- 详情或匹配失败：条目从活动队列移除，进入失败统计/本地最低限度快照，其他条目继续处理。
- 用户取消：立即清空活动队列和延迟状态，显示“正在取消”；同步作业退出后执行现有部分上传。
- 续传和重试：以各自加载的 pending/failure 条目创建新批次队列，不复用上次运行残留的 UI 队列。
- 新同步开始、当前同步结束和详情池下载抑制恢复时清空队列状态。

## 测试策略

1. 进度发布器测试：批次初始化、并发条目开始/完成、跳过项、阶段切换和取消后迟到回调。
2. 同步管理器批处理测试：详情失败、无 IMDb、Trakt 未命中、双登录和豆瓣独立模式的队列变化。
3. 对话框 Compose 测试：列表阶段显示“最近获取”；解析阶段只显示处理/待处理；写入和上传阶段不显示旧条目。
4. 服务通知测试：上传阶段不回退到最近列表项，活动条目优先。
5. 完成后运行定向单元测试、全量 JVM 测试和 debug 构建；若设备在线，再安装并检查同步对话框 UI 树、截图和崩溃缓冲。
